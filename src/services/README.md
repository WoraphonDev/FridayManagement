# Guarded feature services

T-011 authorization uses `SessionProof` from the trusted T-014 token parser/session resolver. Never resolve identity from request body/query IDs. Call `currentActor`/`authorizeOperation` and execute queries/mutations/effects in the same provider transaction; the SQLite writer transaction and SQL SERIALIZABLE reads protect current account/membership state through commit.

`authorizationHooks` binds protected handlers and the T-010 idempotency hook. Handlers use `context.transaction`, never a nested transaction. The supplied session resolver must match the middleware principal. `context.transaction` is only supplied by this guarded invocation. Session creation/cookie parsing/rotation/activity updates still belong to T-014/T-015; reading authorization never extends idle age.

For version-bearing writes, supply `checkVersions` with feature-specific comparisons/locks only. It runs after current rights/resource visibility and before archived/deleted business checks; an unavailable validator fails503. Mutation/audit/notification and schema-checked response persistence follow in the same transaction. Replay checks current rights and cached resource/successor visibility without repeating version/business mutation.

Use `access-scope` builders with the verified caller ID. They apply current visibility in SQL to rows/counts/search/report/export/notification updates, not after fetching private data. These are foundational scopes: Task filters/pagination use the T-031 shared query builder; Calendar/Report/Export consumers, CSV streaming and file bytes remain their feature tasks. Workspace directory/membership DTOs and task-detail DTO assembly have local service evidence. For an explicitly selected archived project, a trusted feature service can enable `includeArchived` after checking project access. Normal report/export defaults exclude archived/deleted tasks; trash uses manage-only scope.

No service starts timers, creates sessions, seeds data or enables protected production routes by import. Real SQL2022 lock/revocation tests remain required.

`taskService` (T-026–T-029) shares the supplied guarded transaction for version checks, task/checklist mutations, board ordering, recurrence tombstones, audit and assignment/status notifications. Acquire canonical board columns before the explicit parent task update lock; subtask writes share the parent version. Recurrence DTOs never clone comments/files/source activity. Current assignee rights are rechecked when reopening and generating the next round. Native SQL2022 locking/concurrency/effects evidence is still NOT_RUN. `organizationService` (T-025) exposes authenticated reads/Admin-only versioned names; public meta remains an installer responsibility.

T-030–T-034 adds manage-only trash, versioned soft delete/30×24-hour UTC restore, shared task SQL filters with scoped count-before-pagination, and ordered four-column board snapshots. At >500 tasks the board returns list_required with empty incomplete columns; clients must use the paginated list. Restore idempotent replay requires current management rights and an active restored cached task; deletion again hides the old cached response. Native SQL collation/locking acceptance remains separate.

T-035–T-039 adds atomic board move using the same completion/reopen/recurrence mutation as detail changes; affected columns are renumbered/bumped once. Three columns can change when doing/review→done creates a todo successor, so contract1.0.1 expands the response bound2→3. Same-column reorder changes task/column versions without regenerating recurrence. Current column/task versions and anchor visibility are checked before mutation. Comments are append-only plain text; comment/event/current eligible recipients persist in the same transaction and route idempotency handles retries. SQL2022 evidence remains NOT_RUN.
